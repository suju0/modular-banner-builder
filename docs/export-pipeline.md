# Export 파이프라인 & 이미지 처리 (Phase 1)

v0.2 에서 추가된 4개 기능(이미지 업로드/누끼, 이미지 Export, 배치 ZIP, 드래그 위치 조정)의
설계 근거와 주의점을 정리한다.

## 1. 렌더 구조 리팩터링 — "보이는 것 = 내려받는 것"

v0.1 의 프리뷰는 **컨테이너 크기만** 축소했다.

```js
// v0.1 (문제)
const scale = Math.min(maxWidth / size.w, 420 / size.h);
<div style={{ width: size.w * scale, height: size.h * scale }}>   // 박스는 축소
  <div style={{ fontSize: bannerSize.h * 0.035 }}>...</div>       // 글자는 원본 크기
```

박스는 줄어드는데 폰트 크기는 배너 원본 기준으로 계산되어, 프리뷰에서 본 균형이
실제 결과물과 달라진다. 여기서 캡처한 이미지를 다운로드하면 그 오차가 그대로 굳는다.

v0.2 는 렌더 계층을 셋으로 나눠 이 문제를 구조적으로 제거했다.

| 컴포넌트 | 역할 |
| --- | --- |
| `BannerRenderer` | **항상 원본 픽셀 크기(size.w × size.h)로** 배너를 렌더하는 순수 컴포넌트 |
| `BannerPreview` | `BannerRenderer` 를 CSS `transform: scale()` 로 축소 표시 + 편집 UI |
| `lib/exportImage.js` | 화면 밖 스테이지에 `BannerRenderer` 를 다시 렌더해서 캡처 |

프리뷰와 Export 가 **같은 컴포넌트**를 쓰므로 두 결과는 정의상 일치한다.
프리뷰 배율(우측 하단 `프리뷰 xx%`)은 표시용일 뿐 결과물에 영향을 주지 않는다.

### 캡처를 프리뷰 DOM 에서 하지 않는 이유
- 프리뷰는 `transform: scale()` 이 걸려 있어 캡처 시 해상도가 배율만큼 손실된다.
- 편집 모드의 점선 아웃라인/라벨/가이드가 함께 찍힌다.
- 사이즈를 바꾸지 않고도 다른 사이즈를 Export 해야 한다(배치 ZIP).

## 2. 캡처 구현 (`lib/exportImage.js`)

`html-to-image` 사용. DOM → SVG `foreignObject` → canvas → Blob 경로다.

```
renderBannerBlob(config, { format, scale })
  ├─ 화면 밖 host(left:-100000px) 에 createRoot + flushSync 로 동기 렌더
  ├─ waitForNode      : DOM 커밋 확인
  ├─ waitForImages    : <img> 로딩 + document.fonts.ready 대기
  ├─ getFontEmbedCSS  : 폰트를 dataURL 로 인라인 (세션 내 1회 캐시)
  └─ toBlob / toJpeg  : pixelRatio = 배율(1x/2x/3x)
```

### 알아야 하는 함정들

**폰트 임베드는 반드시 캐시한다.**
`getFontEmbedCSS()` 는 Pretendard 서브셋 woff2 를 모두 가져와 dataURL 로 바꾼다(첫 실행 ~5초).
결과를 모듈 스코프에 캐시해 두면 두 번째 이후 캡처는 **50ms 수준**으로 떨어진다.
배치 Export 6종이 빠른 이유가 이것이다.
앱 로드 1.5초 뒤 `prewarmFontEmbed()` 로 미리 계산해 첫 클릭의 체감 대기도 줄인다.

**첫 캡처는 한 번 버린다(워밍업).**
`html-to-image` 는 첫 호출에서 리소스 캐시가 비어 폰트/이미지가 누락된 결과를 내는
알려진 이슈가 있다. 세션당 1회만 결과를 버리고 다시 캡처한다.

**백그라운드 탭에서는 캡처가 멈춘다.**
`html-to-image` 내부(`createImage`)가 `requestAnimationFrame` 으로 완료를 통보하는데,
브라우저는 숨겨진 탭에서 rAF 를 호출하지 않는다 → 프로미스가 영구 대기한다.
그래서 캡처를 `captureWithVisibilityGuard()` 로 감쌌다.

- 시작 전 `document.hidden` 이면 `visibilitychange` 까지 대기하고, UI 에 안내 문구를 띄운다
- 캡처가 20초를 넘기면 최대 3회까지 재시도하고, 그래도 안 되면 "브라우저 창을 활성화한
  상태에서 다시 시도해 주세요" 로 명확히 실패시킨다 (캡처는 DOM 을 읽기만 하므로 재시도 안전)
- 창이 다른 창에 완전히 가려진 경우 `visibilityState` 는 `visible` 이면서도 rAF 가 멈출 수
  있어, `hidden` 여부만으로 판단하지 않는다

마케터가 일괄 생성을 걸고 다른 탭으로 넘어가는 건 흔한 시나리오이므로 필수 방어다.

**단일 라인 모듈에는 `white-space: nowrap` 을 준다.**
`eventTag` / `discount` / `date` 는 설계상 한 줄이다. 폰트 임베드 결과에 따라 글자
너비가 미세하게 달라지면 프리뷰에선 한 줄, 결과물에선 두 줄이 되는 어긋남이 실제로
발생했다. 줄바꿈을 금지해 두 렌더를 일치시킨다.
(`title` / `subtitle` 은 `maxW` 로 폭이 고정되어 있어 동일하게 줄바꿈된다.)

## 3. 배치 Export (ZIP)

`exportBatchZip()` — **현재 레이아웃 채널(웹/앱)의** 사이즈 프리셋을 **직렬로** 렌더한다.
앱 레이아웃으로 PC 풀배너를 뽑는 건 의미가 없어 범위를 채널로 제한한다. 병렬 처리는 폰트 임베드와
canvas 메모리가 동시에 몰려 대형 사이즈에서 실패하기 쉽다.

ZIP 구성:

```
컬리-프레시-페스타_center-festa_purple_720x480.png
컬리-프레시-페스타_center-festa_purple_1200x400.png
... (사이즈별)
manifest.json      ← 생성 시각, 레이아웃/테마/콘텐츠/모듈 스냅샷
```

`manifest.json` 을 함께 넣어 두면 "이 배너 어떤 설정으로 뽑았지?" 를 나중에 추적할 수 있고,
Phase 2 의 에셋 관리 대시보드가 읽을 메타데이터가 된다.

## 4. 배경 제거(누끼) — 프로바이더 교체형

`lib/removeBackground.js` 는 4개 프로바이더를 같은 인터페이스로 감싼다.

| id | 방식 | 설정 | 품질 |
| --- | --- | --- | --- |
| `region` | 남길 영역 지정 + 플러드필 (로컬) | 없음 | 단색 배경 상품컷에 실용적 |
| `removebg` | remove.bg API | `VITE_REMOVEBG_API_KEY` | 상용 최고 |
| `endpoint` | 사내 rembg / BiRefNet | `VITE_BG_REMOVE_ENDPOINT` | 서버 모델에 따름 |
| `imgly` | 브라우저 AI (CDN 런타임 로드) | 없음 | 좋음 (최초 모델 ~40MB) |

기본값은 `detectProvider()` 가 환경변수를 보고 고른다(키가 있으면 API, 없으면 `region`).

### 왜 AI 모델을 기본 의존성으로 넣지 않았나
`@imgly/background-removal` 은 **AGPL-3.0** 이다. 사내 어드민이라도 웹으로 배포되는
형태에서는 소스 공개 의무가 문제될 수 있어 `package.json` 에 넣지 않았고,
선택 시에만 CDN 에서 런타임 로드한다(번들 미포함). 상업적 사용 전 법무 검토 권장.

실무 권장 구성은 **`endpoint` + 사내 rembg 서버**다. 키 노출이 없고, 원가가 고정이며,
`VITE_` 환경변수가 클라이언트에 노출되는 문제도 피할 수 있다.

### `region` 알고리즘 — 왜 "허용 범위 슬라이더"를 버렸나
초기 구현은 허용 오차를 슬라이더로 받았다. 그런데 마케터 입장에서 "35%"가 무슨
뜻인지 알 수 없고, 결과를 보고 감으로 다시 맞추는 반복 작업이 된다.
**남길 영역을 사각형으로 직접 지정**하면 의도가 그대로 입력되고, 허용 오차는
이미지에서 자동 추정할 수 있다.

1. 선택 영역(0~1 정규화 사각형) **밖은 완전히 제거**
   - 경계를 페더링하지 않는다. 반투명 테두리를 남기면 트리밍 후에도 상품 주변에
     사각 여백이 생겨 슬롯에서 상품이 작게 배치된다(실제로 발생한 문제).
2. 영역 **테두리 픽셀**에서 배경색(중앙값)과 산포도(평균 절대편차)를 추정
   - 허용 오차 `hardTol = clamp(14 + 산포도 × 1.5, 16, 55)` — 배경이 균일하면 좁게,
     노이즈가 있으면 넓게 자동 조정
3. 영역 테두리에서 안쪽으로 BFS 플러드필 → 상품 주변에 남은 단색 배경 제거
   - 색 거리 ≤ `hardTol` → 완전 투명, 이웃으로 확산
   - `hardTol` ~ `softTol`(1.9배) → 부분 알파(경계 페더링), 확산 중단
4. 투명 여백 트리밍(`trimTransparent`) → 배경에 꽉 차게 배치
5. 제거 면적이 2% 미만 / 98.5% 초과면 경고를 띄운다

영역을 지정하지 않고 실행하면 이미지 전체를 대상으로 3~5 단계만 수행한다
(= 예전 `flat` 동작). 내부(구멍) 배경은 테두리에서 도달할 수 없으므로 남는다 —
의도된 동작이다.

### 되돌리기
누끼 결과는 원본을 덮어쓰지 않고 `image.cutoutSrc` 에 따로 보관한다.
- `useCutout` 토글: 원본/누끼 표시 전환 (결과는 보존)
- "누끼 취소": `cutoutSrc` 를 버리고 완전히 원본 상태로 복귀

## 4-1. 배경 이미지 변형 (포토샵 자유 변형)

`lib/imageTransform.js` 의 모델은 `{ scale, x, y }` 세 값이다.

- `scale 1` = 캔버스를 꽉 채우는 크기(cover). 누끼 이미지는 contain 기준
- `x, y` = 캔버스 크기에 대한 비율 이동값 (0.1 = 캔버스 너비의 10% 이동)

비율 좌표를 쓰기 때문에 배너 사이즈를 바꿔도 구도가 유지된다.
(v0.2 의 crop 사각형 모델보다 핸들 리사이즈·휠 줌 계산이 단순하고,
포토샵 자유 변형의 조작 감각과 1:1로 대응한다)

```
computeImageLayout({ transform, source, canvasW, canvasH, fit })
  → { drawW, drawH, left, top }
```

조작은 `components/Canvas/ImageTransformEditor.jsx` 가 담당한다.

- **8개 핸들** (코너 4 + 엣지 중앙 4, 흰 정사각형 + 파란 테두리)
- 핸들 드래그 → 비율 유지 리사이즈. 잡은 핸들의 **반대쪽 지점을 고정점**으로 잡고
  `resizeTransformByHandle()` 이 고정점이 제자리에 남도록 x/y 를 다시 계산한다
- 본체 드래그 → 이동, 마우스 휠 → **커서 아래 지점을 고정한** 확대·축소(`zoomAt`)
- 크기가 바뀌면 우하단에 비율 뱃지(예: 150%)를 1.2초 표시
- 사이드바 `ImageAdjustPanel` 은 같은 값을 수치로 조작한다(슬라이더·방향키·초기화)

### 알아야 하는 함정
**휠 이벤트는 네이티브로 등록해야 한다.** React 의 `onWheel` 은 passive 리스너로
붙어서 `preventDefault()` 가 통하지 않는다 → 페이지가 함께 스크롤된다.
그래서 `addEventListener("wheel", fn, { passive: false })` 로 직접 등록한다.

**핸들 표시 좌표는 캔버스 안으로 당겨 둔다.** cover 기본값에서는 이미지 박스가
캔버스보다 커서 코너 핸들이 `overflow: hidden` 에 잘려 잡을 수 없다.
계산은 실제 좌표로 하고 **표시 위치만** 클램프한다.

## 4-1-1. 배경 확장 (생성형 확장) 과 내용 인식 비율

배너에서 텍스트가 놓일 "빈 배경"을 만드는 두 가지 도구.

### 배경 확장 — `lib/imageExpand.js`
캔버스를 원하는 방향(좌/우/상/하, 다중 선택)으로 원본의 10~100% 만큼 늘리고
늘어난 영역을 채운다.

| 방식 | 구현 | 적합한 소재 |
| --- | --- | --- |
| 엣지 늘리기 | 가장자리 1px 열을 늘려 채움 | 단색·그라데이션 스튜디오 배경 |
| 미러 + 블러 | 가장자리 스트립을 반사 후 이음선 블러 | 나무결·패브릭 등 질감 배경 |
| AI 아웃페인팅 | 사내 생성 모델 서버(`VITE_OUTPAINT_ENDPOINT`) | 복잡한 실사 배경 |

> **정직하게 적어 둔다: 기본 두 방식은 AI 생성이 아니다.**
> 디퓨전 아웃페인팅은 모델 추론이 필요해 브라우저만으로는 불가능하다. 대신
> 프로바이더를 분리해 사내 추론 서버를 붙일 수 있게 했고(마스크까지 함께 전송),
> 컬리 상품컷처럼 배경이 단순한 소재에서는 엣지 방식 결과가 생성형과 구분되지 않는다.

좌우를 먼저 채우고 상하를 캔버스 전체 폭으로 채우면 **코너가 자동으로 메워진다.**
마지막에 원본/확장 경계에만 블러 밴드를 얹어 이음선을 지운다.

### 내용 인식 비율 — `lib/seamCarve.js`
에너지가 가장 낮은 이음선(seam)을 찾아 복제/제거해 피사체는 그대로 두고
여백만 늘린다. 3:2 상품컷을 5.3:1 풀배너에 쓰려고 할 때 단순 늘리기(왜곡)나
크롭(잘림) 대신 쓴다.

구현에서 실제로 부딪힌 문제와 대응:

1. **원본 해상도로 돌리면 브라우저가 멈춘다** (비용 = 픽셀 수 × 심 개수).
   → 심 탐색은 축소본(긴 변 560px)에서, 적용은 원본 해상도에서 한다.
   "열별 복제 횟수"만 확대 적용하면 결과가 사실상 같다.
2. **심마다 배열을 새로 만들면 GC 때문에 18초** 걸렸다.
   → 버퍼를 미리 잡아 재사용하고 심 제거를 in-place 로 처리 → **0.7초**.
3. **단색 피사체의 내부는 에너지가 0** 이라 심이 상품을 관통해 지나간다
   (테스트 이미지의 원·타원이 가로로 찢겼다).
   → 테두리에서 배경색을 추정해 "배경과 다른 픽셀"에 비용을 더하는 보호항을 넣고,
   윤곽을 스치지 못하도록 보호맵을 가로로 3px 팽창시켰다.
4. **배경 여유보다 많은 심을 요구하면** 결국 피사체를 자른다.
   → 심의 누적 비용이 한계를 넘으면 조기 중단하고, 적용된 양과 함께 안내한다.
5. **행마다 삽입 수가 달라 물체 경계가 들쭉날쭉해진다.**
   → 누적 변위를 세로로 평활화(prefix sum → 세로 평균 → 차분)해 경계가 매끄럽게 밀리게 했다.

한 번에 늘릴 수 있는 한계는 1.6배(심 220개)다. 그 이상은 여러 번 실행하거나
배경 확장과 함께 쓰라고 안내한다. 실무 조합은 **내용 인식 비율 → 배경 확장** 순서다.

편집 결과는 `image.src` 를 교체하고 업로드 원본은 `image.baseSrc` 에 남긴다
(`edits` 배열에 이력 표시, "업로드 원본으로 되돌리기" 가능). 소스가 바뀌면
이전 누끼 결과는 무효이므로 함께 비운다.

## 4-2. 컬러 — 테마 + 역할별 오버라이드

테마는 "출발점"이고, 최종 색은 역할별 오버라이드가 결정한다.

```
resolveTheme(themeId, overrides) → { bg, text, sub, accent, badge, badgeText }
```

프리뷰(`BannerPreview`)·렌더(`BannerRenderer`)·Export(JPG 배경색)가 **모두 이 함수를
거친다.** 색 계산 경로가 하나뿐이므로 프리뷰와 결과물이 갈라지지 않는다.

- 오버라이드는 `COLOR_ROLES`(6개 역할)에 대해서만 허용 — 임의 CSS 를 받지 않는다
- 테마를 바꾸면 오버라이드를 초기화한다(섞이면 결과 예측이 어려움)
- 팔레트 UI(`components/ui/ColorPicker.jsx`)는 그라데이션 피커(native `input[type=color]`) +
  HEX + R/G/B + 스포이드(EyeDropper API, Chromium 계열만) + 테마값 복원을 제공한다
- 스포이드는 지원 브라우저에서만 버튼이 노출된다(`supportsEyeDropper()`)

## 4-3. 배경 미지정(투명) 과 배경 그라데이션

### 배경 없음
`컬러 테마 > 배경 없음` 은 배경 역할을 `transparent` 로 오버라이드한다
(`lib/color.js` 의 `TRANSPARENT` 센티넬 — CSS 값으로 그대로 쓸 수 있어 분기가 줄어든다).

- PNG: 알파가 그대로 저장된다 (텍스트·뱃지만 남는 투명 배너)
- JPG: 알파를 지원하지 않아 **흰색으로 채운다** (`exportImage.js` 에서 분기).
  밝은 텍스트 색이면 결과가 보이지 않으므로 UI 에 경고 문구를 띄운다
- 프리뷰 프레임도 칠하지 않아 체커 패턴이 보인다 = 투명임을 눈으로 확인할 수 있다

앱 UI 위에 얹는 배너, 다른 배경과 합성할 소재를 뽑을 때 쓴다.

### 배경 그라데이션
사진 위에 텍스트를 얹으면 사진 밝기에 따라 가독성이 무너진다. v0.1 은 이걸
`linear-gradient(135deg, bg+ee, bg+88, bg+22)` 하드코딩으로 덮었는데, 방향·세기·범위를
바꿀 수 없어 사진마다 결과가 들쭉날쭉했다.

이제 `lib/gradient.js` 의 설정값으로 뺐다.

```js
{
  enabled: true,
  angle: 90,          // CSS 기준 90deg = 왼쪽 → 오른쪽
  from: null,         // null = 테마 배경색을 따라감 (테마 바꾸면 같이 바뀜)
  fromOpacity: 0.92,  // 텍스트 쪽 — 대비 확보
  to: null,           // null = 미지정 = 완전 투명 (사진 그대로 노출)
  toOpacity: 0.15,
  midpoint: 45,       // from 색이 유지되는 지점(%) — 텍스트 영역 폭에 맞춘다
}
```

```
resolveGradient(gradient, theme)
  → linear-gradient(90deg, C1 0%, C1 45%, C2 100%)
```

- 끝 색 미지정은 `transparent` 키워드가 아니라 **`rgba(from, 0)`** 으로 만든다.
  `transparent` 는 일부 렌더러에서 투명한 검정으로 보간되어 중간이 탁해진다
- `from` 을 null 로 두는 것이 기본값이다. 테마를 바꿔도 그라데이션이 따라오므로
  "테마만 바꿔서 여러 안 뽑기" 흐름이 깨지지 않는다
- 테마 배경까지 미지정이면 기준색이 없으므로 `#111111` 로 대체한다
- `isGradientVisible()` 로 완전 투명인 경우엔 레이어를 아예 렌더하지 않는다
  (Export 시 불필요한 노드를 줄인다)

사이드바 `GradientEditor` 는 **배경 이미지가 올라와 있을 때만** 나타난다(그라데이션의 목적이
사진 위 가독성 확보이므로). 방향 프리셋 4종 + 각도 슬라이더 + 시작/끝 색 + 불투명도 +
전환 지점을 제공하며 결과를 미리보기 바로 보여준다.

## 5. 드래그 위치 미세 조정

`@dnd-kit` / `react-dnd` 대신 포인터 이벤트로 직접 구현했다.
이 기능은 리스트 정렬이 아니라 **축소된 캔버스 위의 자유 좌표 이동**이라,
드래그 라이브러리의 추상화(센서/충돌 감지/드롭 타깃)가 오히려 걸림돌이 된다.
필요한 것은 `화면 이동량 ÷ 프리뷰 배율 → % 변환` 한 줄이다.

```js
dx% = (e.clientX - startX) / (bannerSize.w * previewScale) * 100
```

- 오프셋은 **% 단위**로 저장 → 배너 사이즈를 바꿔도 상대 위치 유지
  (`docs/slot-system.md` 의 "비율 유지" 요구사항)
- 저장 구조는 `{ [layoutId]: { [moduleId]: { dx, dy } } }` — 레이아웃마다 슬롯 좌표가
  다르므로 레이아웃별로 분리한다
- 스냅: 원위치(±0.8%) / 캔버스 중앙(50%) 자동 스냅, 드래그 중 중앙 가이드 표시
- 키보드: 방향키 0.5%, `Shift` + 방향키 2%, `Backspace` 로 해당 슬롯 초기화, `Esc` 선택 해제
- 편집 UI 는 `previewScale` 의 역수를 곱해 화면상 두께/글자 크기를 일정하게 유지한다

## 폰트 임베드 — 조용히 폴백되는 함정 (실제로 겪음)

`html-to-image` 는 foreignObject 안에서 외부 폰트를 참조할 수 없어, @font-face 의
폰트 파일을 base64 로 CSS 에 인라인한다. 이때 `preferredFontFormat` 옵션은
**format() 문자열을 정확히 문자 비교**한다 (embed-webfonts 의 filterPreferredFontFormat).

일치하지 않으면 경고 없이 **src 선언 전체를 삭제**한다. 결과물에는 @font-face 가
남지만 가리키는 파일이 없어, Export 가 **조용히 폴백 폰트로** 렌더된다.
자간·글자폭이 달라져 Figma 기준 좌표가 통째로 어긋나는데 에러는 전혀 나지 않는다.

실제 사례: globals.css 가 Pretendard 공식 CSS 를 따라
`format('woff2-variations')` 로 적혀 있었고 Export 는 `preferredFontFormat: 'woff2'`
를 넘겼다 → 임베드 CSS 가 111바이트(= src 없는 껍데기)로 나왔다.

더 나쁜 건 이 필터가 **비결정적**이라는 점이다. `URL_WITH_FORMAT_REGEX` 가
모듈 스코프의 `/g` 정규식인데 `lastIndex` 를 초기화하지 않고 `exec` 한다
(embed-resources.js:39-53). 그래서 **같은 입력이라도 호출 횟수에 따라 결과가 바뀐다.**

실측 (같은 노드로 5회 반복):

| 호출 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| `preferredFontFormat` 사용 | src O | src X | src O | src X | src O |
| 미사용 | src O | src O | src O | src O | src O |

즉 **Export 두 번에 한 번꼴로 폰트가 통째로 빠진 채** 나가고 있었다.

규칙
- **`preferredFontFormat` 을 넘기지 않는다.** @font-face 가 woff2 하나뿐이라
  걸러낼 포맷도 없고, 옵션을 쓰는 순간 위 버그에 노출된다.
- @font-face 의 format 은 `woff2` 로 적는다 (`woff2-variations` 아님).
  가변 축은 format 표기와 무관하게 동작한다.
- `computeFontEmbedCSS` 에 안전망이 있다 — 규칙은 있는데 `src:` 가 없으면 경고를 남긴다.

### 비용과 캐시
단일 woff2(약 2MB) 자체 호스팅 기준 임베드 비용은 **콜드 37ms / 웜 5ms** 다.
(예전 5~6초는 CDN 동적 서브셋 100여 개를 개별 fetch 하던 시절 수치다.)
그래도 모듈 스코프 promise 로 캐시하고 앱 진입 1.5초 뒤 `prewarmFontEmbed()` 로
미리 돌린다 — 첫 화면이 빌더 목록이라 고르는 동안 준비가 끝난다.

**실패는 캐시하지 않는다.** 예전에는 `.catch(() => "")` 결과까지 캐시돼서,
일시적인 fetch 실패 한 번이 그 세션의 모든 Export 를 폴백 폰트로 만들었다.

폰트가 아직 로딩 중이면(`font-display: swap`) 폴백으로 그려진 상태를 캡처하게 되므로,
`waitForFonts()` 가 `document.fonts.ready` 를 최대 5초까지 기다린 뒤 진행한다.
실패시키지 않고 진행하는 쪽을 택했다.

## 백그라운드 탭 — 전체 상한이 없으면 영구 pending

`html-to-image` 내부(createImage)가 rAF 로 완료를 알리는데 브라우저는 숨겨진 탭에서
rAF 를 호출하지 않는다. 그래서 캡처 전에 탭 가시성을 확인한다.

예전 구현의 구멍: **`waitUntilVisible()` 에 상한이 없었다.** 20초 타임아웃은
캡처에만 걸려 있어서, 탭이 끝내 돌아오지 않으면 Export promise 가 영원히 pending 이었고
호출부의 finally 가 돌지 않아 진행 표시도 그대로 남았다.

현재 `captureWithVisibilityGuard` 의 계약
- **전체 상한 90초** — 탭 대기 시간까지 포함한다. 초과하면 명확히 reject.
- 시도당 20초, 최대 3회. 캡처는 DOM 을 읽기만 해서 재시도가 안전하다.
- html-to-image 는 취소 수단이 없어 타임아웃된 시도도 계속 돈다. 그래서 **버린 시도를
  버리지 않고** 다음 라운드 경합에 함께 넣는다. 느리게라도 끝나면 그 결과를 쓰고,
  race 가 가장 먼저 끝난 하나만 반환하므로 결과가 뒤섞이지 않는다.
- 버려진 시도의 rejection 은 finally 에서 삼켜 unhandled 로 남기지 않는다.
- `renderBannerBlob(config, { attemptTimeoutMs, totalTimeoutMs })` 로 상한을 조절할 수 있다.

## 색 정확도 — 숫자는 맞는데 달라 보이는 경우

실측 결과 미리보기와 Export 모두 지정값과 **정확히 일치**한다.

| 대상 | 값 |
| --- | --- |
| 테마 지정값 | `#5F0080` |
| 미리보기 DOM (computed) | `rgb(95, 0, 128)` |
| Export 픽셀 (좌상/중앙/우하) | `rgb(95, 0, 128)` |

조상 노드에 `filter`·`opacity`·`mix-blend-mode` 도 없다. 즉 앱에는 색 오차가 없다.

그럼에도 "미세하게 달라 보인다"가 나오는 이유는 두 가지다.

1. **색공간 태그** — canvas 가 만든 PNG 에는 색공간 표시가 없다. 브라우저는 태그 없는
   이미지를 sRGB 로 보지만, 뷰어·디자인 툴 중에는 모니터 프로파일로 해석하는 것이 있어
   같은 픽셀값이 다른 색으로 보인다. → `lib/pngColorProfile.js` 가 PNG 에 sRGB/gAMA/cHRM
   청크를 붙인다. **픽셀 데이터(IDAT)는 한 바이트도 바뀌지 않고** 파일만 73바이트 늘어난다.
   같은 파일에 두 번 돌려도 중복으로 붙지 않는다.
2. **대비 착시** — 미리보기는 밝은 회색 배경 위의 작은 카드이고 추출물은 화면을 꽉 채운다.
   같은 색도 주변 밝기에 따라 다르게 보인다. 이건 코드로 고칠 수 있는 문제가 아니다.

JPG 는 태그하지 않는다. 손실 압축이라 평면 색도 미세하게 흔들리고, 태그 없는 JPEG 는
거의 모든 뷰어가 sRGB 로 가정한다. **색이 정확해야 하면 PNG 를 쓸 것.**
